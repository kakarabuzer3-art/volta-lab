## Minimal UI redesign and LCD / protective-trip fix (on top of `f2952b0`)
**Root cause (traced through the engine, the display painter and the browser).** Switching AC/DC never touches Main Power, SOC or the engine state (`setInputs` only resets the protection timers on a mode change). What the report describes is the latched **overcurrent trip**: with the cable ends touching, the output sits in current limit and after the 2 s trip delay the protection latches, the output current drops to 0 (so the spark / wire effect stops) while `inputs.powerOn` stays true (so the physical switch still reads ON). The LCD painter treated the "tripped" state as not live and used its dim unlit palette, so a powered, tripped machine looked switched off. Changing the mode just happened to coincide with the trip. Nothing forced the display or the animation on; the fix is in how the display state is derived.
**Fix.** `displayPresentation(snapshot)` in `src/sim/status.ts` is now the single source of truth for the LCD: lit exactly when Main Power is ON, a fault message for trip / thermal shutdown / empty battery, mode label from the snapshot. The wire / spark effect was already derived from the snapshot each frame (short and current > 0), so there is no separate AC/DC render state to go stale. Trips stay latched until Main Power is cycled (unchanged protection behaviour).
**Interface.** Header: only Controls, Wide View, View Free (right-aligned; the Controls label collapses to an icon at 420 px and below, its accessible name stays "Controls"). Removed from the scene: title and subtitle, Learning Hub and Limitations links, Simulation-only badge, Help button, first-visit Quick Start toast, X/Y/Z readout, lead labels, output-status badge, footer status text, instruction strip, floating voltage card (the machine's own LCD stays). One panel with five tabs: Controls, Settings (camera behaviour, motion note), Help (operation, wires, shortcut table), Learning Hub (links to the existing lessons), Limitations & Safety. The short-circuit warning stays inside the Output Cables card. The Wide View button names the current view and its accessible name says what a click does.

## QA correction pass (after `9273acf`)
The touch-camera checks now classify each gesture from the real orbit target (a test-readable DOM diagnostic attribute, `data-camera-target`, on the canvas, written by the HUD loop each frame) plus the camera position:
`orbit` (direction from the target changed; distance and target unchanged), `zoom` (distance changed; direction and target unchanged), `pan` (target moved; distance and direction unchanged) or `none`.
Expected: FREE = orbit / zoom / pan for rotate / pinch / pan; LOCKED = none for all three; ZOOM ONLY = none / zoom / none; ROTATE ONLY = orbit for all three. In ROTATE ONLY the two-finger gestures **orbit** because of how the installed
OrbitControls (three.js r186, read from its source) handles a second finger when zoom and pan are both off (`onTouchStart`, two-pointer case returns without changing the one-finger rotate state). The checks assert that actual behaviour
(orbit occurred, no zoom, no pan, same distance, same target); a different three.js version could behave differently and the check would flag it. These are emulated touch events in desktop Chromium, not physical-device tests.

**About `data-camera-target`.** It is a diagnostic DOM attribute that the browser check reads. The application has no camera-control setter that uses it and no public camera API was added. It is **not** technically immutable or inherently read-only: it is an ordinary DOM attribute, so page JavaScript (or DevTools) can modify it, and the HUD loop simply overwrites it on the next frame. Camera behaviour is driven by OrbitControls and `cameraMode`, never by this attribute.
